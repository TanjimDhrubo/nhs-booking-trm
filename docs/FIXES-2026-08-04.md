## 6. Dependent appointment — fixed (PRN-based)
- When "A dependent / family member" is chosen in `book.html`, the old empty dependents dropdown is replaced with a **PRN (Patient Reference Number)** field.
- On Review: PRN is validated (10-digit, no leading 0) and checked via new SECURITY DEFINER RPC `verify_patient_prn(text)`.
  - Not registered → inline alert **"Patient is not registered — they need to create an account first"** with a Register link.
  - Registered → choice card shows **"Booking for <name>"**.
- On Book Now: new SECURITY DEFINER RPC `book_dependent_appointment(text, uuid, text, timestamptz)` inserts the appointment **under the PRN patient's own account** (bypasses RLS so the guardian can't directly insert) and inserts a notification to that patient. Appointment shows in *their* dashboard/history/check-in.
- `confirmation.html?id=...&booked_for=<name>` renders a guardian success card (fetches doctor name from the publicly-readable doctors table; no RLS conflict since the guardian can't read the dependent's appointment).
- `questionnaire.html` got the same dependent branch (RPC instead of self-insert) and passes `booked_for` on redirect.
- Security note: any authenticated user can book for any registered patient whose PRN they know. Acceptable for this NHS demo; a real system would gate this (e.g., guardianship records).
- New DB objects (migration `dependent_prn_booking`): `verify_patient_prn`, `book_dependent_appointment` — `SECURITY DEFINER`, executed by `authenticated` only.
- Verified end-to-end with audit patient (guardian) booking for "John Doe" (PRN `2757796532`): choice card showed "Booking for John Doe", appointment landed under John Doe's account (`20a85fa5-…`), notification delivered, guardian confirmation card rendered with no console errors. Not-registered path tested with bogus PRN `1234567890` → Register link shown.
